## ② `price_poll` → Pages 구간별 시간 (로그 실측 · 09-03·09-04)

**「5분 안」의 대상 경로와 기산점**: v190 의 약속은 「한국 시세가 09:00:20 부터 5분마다 사이트에」다. 기산점은 **5분 경계(HH:M5:00 KST)**, 대상은
**사이트의 `data/price.json`**(price-data 브랜치 → `gh workflow run pages.yml` → 배포). 화면은 그 위에 열린 탭의 ticker(`PRICE_TICK_MS` = 5분 · 한국장 중)
또는 탭 복귀 즉시 fetch(`?t=` 캐시 우회 · Pages 는 `cache-control: max-age=600` 이지만 URL 이 매번 달라 CDN MISS)가 얹힌다.

| 구간 | 정의 | 09-03 (78건) | 09-04 (79건) |
|---|---|---|---|
| 수집 | 경계 → 스냅샷 로그 | 중앙 22s · max 22s | 22s · 22s |
| 브랜치 반영 + 배포 깨우기 | 스냅샷 → pages run 생성(dispatch) | 2s · 3s | 2s · 3s |
| 배포 | pages run 생성 → 완료 | 22s · 52s | 22s · 42s |
| **경계 → 배포 완료** | dispatch run 기준 | **46s · p90 50s · max 76s** | **46s · p90 49s · max 66s** |
| 경계 → 유효 배포 | dispatch 가 취소된 건은 후속 성공 run 완료 | 46s · max **88s** | 46s · p90 53s · max **349s** |
| 화면 반영 | 유효 배포 → 화면 fetch | 라이브 표본 없음 — ticker 위상 0~5분 또는 탭 복귀 즉시 (관찰 대기) | 〃 |

- 값이 안 바뀐 스냅샷(09-03 7건 · 09-04 6건)은 당시 규약대로 발행 생략(v222 부터는 30분마다 재발행). 발행된 것은 전부 dispatch 와 짝이 맞았다(미매칭 0).
- **dispatch 취소** 09-03 2건 · 09-04 6건. 그중 후속 push/인계 run 이 30~62s 안에 덮은 것 외에 **09-04 3건(11:55·13:30·13:55)은 다음 스냅샷까지 341~349s**
  늦게 반영됐다. 연쇄(실측): 예비 슬롯(:20/:50, 동시성 그룹 대기)이 다음 예약에 밀려 **취소**됨 → `price` 의 `workflow_run(completed)` 이벤트 → pages 새 run
  생성(:55:32) → 워크플로 수준 `concurrency: cancel-in-progress` 가 **진행 중인 5분 dispatch 배포(:55:24)를 취소**(:55:35) → 그 run 자신은 skipped(0 스텝).
- **판단**: 이틀 표본에서 「경계 → 사이트」는 1분 남짓이 통상이고, 한 번의 성공이 아니라 157건의 분포다. 그러나 **상시 보장은 아니다** — 예약 실행 지연은
  v190 실측대로 분 단위로 흔들리고, 위 취소 연쇄가 하루 2~3번 5분을 먹는다. 화면까지의 시간은 ticker 위상 때문에 최대 약 6분이며 라이브 표본은 없다.
- **인계(공용 워크플로 · 미수정)**: `pages.yml` 후보 — ⓐ `concurrency` 를 job 수준으로 내려 skipped 될 run 이 진행 중 배포를 못 죽이게 하거나 ⓑ `workflow_run`
  트리거에서 `conclusion == 'cancelled'` 를 걸러 낸다(g_deploy 의 「`conclusion == 'success'` 금지」 검사와 충돌 없음). 어느 쪽이든 dispatch 실측으로 확인 뒤 적용.
