## 1. 라이브 종가 미갱신 — 원인과 수정

### 무슨 일이 있었나

| 시각(UTC) | 사건 |
|---|---|
| 2026-08-25 23:42 | 예약 실행 **성공** (8/25 종가 반영) |
| 2026-08-26 22:30 | 예약 실행 **누락** ← 여기 |
| 2026-08-27 01:25 | 수동 실행 → 8/26 종가 711.37 반영 |

**`daily-signal` 워크플로 자체는 정상이다.** 8/25 예약분은 제대로 돌았다.
8/26 22:30 UTC 슬롯이 **실행 자체가 생성되지 않았다** — GitHub Actions 의
알려진 동작으로, 플랫폼 부하가 높으면 예약 실행을 지연시키거나 **통째로 버린다**.
(GitHub 문서에도 "높은 부하 시 실행이 지연되거나 삭제될 수 있다"고 명시돼 있다.)

### 수정 — 예비 슬롯 2개

```yaml
- cron: '30 22 * * 1-5'   # 07:30 KST — 기존
- cron: '30 23 * * 1-5'   # 08:30 KST — [v35] 예비 1
- cron: '30 0 * * 2-6'    # 09:30 KST — [v35] 예비 2
```

한 번 놓쳐도 **한국장 개장(09:00 KST) 전에 따라잡는다.**
이미 최신이면 `git diff --staged --quiet` 로 "변경 없음" 처리되므로 중복은 무해하다.

> **한계**: 세 슬롯이 모두 버려질 수도 있다. 완전한 해결은 외부 스케줄러
> (cron-job.org 등)로 `workflow_dispatch` 를 호출하는 것이지만, 그건 외부
> 의존성을 하나 더 만든다. 화면 상단에 `as_of` 날짜가 늘 보이므로
> **날짜가 이틀 이상 밀렸으면 수동 실행하면 된다** (Actions 탭 → 일일 신호 갱신 → Run workflow).

## 3. ★ 시점별 재계산 — 미래참조의 결정적 검사

정규식도 AST 도 "이 벡터 연산이 미래를 보는가"를 답하지 못한다.
**유일한 방법은 날짜별로 데이터를 잘라 다시 계산해보는 것**이다.
잘린 데이터로 만든 값이 전체 데이터로 만든 값과 같으면 미래를 안 본 것이다.

무작위 40개 시점에서 재계산:

| 신호 계층 | 불일치 |
|---|---|
| (a) QQQ 252일 낙폭 | **0 / 40** |
| (b) 변동성 z점수 `zc()` | **0 / 40** |
| (c) 확장창 분위 `exp_q()` | **0 / 40** |
| (d) 비중경로 `rule_w()` | **0 / 40** |

**총 불일치 0건.** 신호 사슬 어디에도 미래참조가 없다.

> v34 의 lag 스캔(미래를 당기면 45배)은 **간접 증거**였다.
> 이건 **직접 증거**다 — 그날 서 있었다면 정확히 같은 숫자를 봤을 것이다.
